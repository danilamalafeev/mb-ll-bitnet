# E15 — регистровый интерпретатор ADD/XOR/SWAP

Статус: **DRAFT / NOT CLEARED**, без нейросетевого обучения. Этот вариант
заменяет прежний кандидат `E15_OPERATION_COMPOSITION_PROPOSAL.md`, который
сохраняется как история. Основание — предложение пользователя и локальный
точный аудит; литературные численные утверждения из предложения здесь не
перепроверены и не используются как экспериментальное evidence.

## Вопрос

Может ли фиксированное рекуррентное QAT-ядро исполнять знакомые инструкции
в новых сочетаниях при знакомой длине программы? Сравнение с GRU показывает
качество двух систем на одной задаче; оно не изолирует эффект квантования,
четырёх блоков или маршрутизации. Router в E15 отсутствует.

## Семантика и точный аудит

Два регистра x,y в 0..15. ADD: x=(x+y)%16; XOR: x=x xor y;
SWAP: (x,y)=(y,x). Ответ — оба регистра, метрика joint exact match.
Инструкции выполняются слева направо, промежуточные состояния вычисляются
эталонным интерпретатором только для targets/метрик.

`scripts/register_dsl_e15_audit.py` перебрал все 256 состояний и все
39 программ длины 1–3. Evidence:
`results/E15_REGISTER_DSL_SEMANTIC_AUDIT.json`.

- 32 программы без соседства ADD,XOR разрешены для обучения.
- 7 программ содержат запрещённое соседство.
- ADD,XOR,XOR эквивалентна ADD на всех состояниях: отдельный контроль,
  не часть основного критерия композиционного переноса.
- Оставшиеся 6 программ задают 6 разных преобразований, ни одно не
  эквивалентно разрешённой программе на всех 256 состояниях.
- Основной тест: 6×256=1536 примеров, результаты отдельно для каждой программы.
- ADD,XOR против XOR,ADD различаются на 224 состояниях; остальные 32
  нельзя использовать как свидетельство учёта порядка.
- Каждая инструкция представлена на каждой позиции разрешённых программ
  каждой соответствующей длины; точное покрытие сохранено в audit JSON.

Эквивалентность всего преобразования не исключает совпадений на части входов.
Для перестановочных пар дополнительно считать joint correctness только на
состояниях, где эталонные ответы различаются. Фильтр определяется семантикой
до обучения, а не ошибками модели.

## Разбиение и выбор checkpoint

Предлагаемое детерминированное разбиение 256 начальных состояний: отсортировать
по SHA256 от ASCII-строки `E15-state-v1:x:y`, взять первые 192 для train,
следующие 32 для validation, последние 32 для обычного test. Общий split
для всех программ, обеих моделей и seeds. До обучения материализовать и
зафиксировать hashes, проверить непересечение и покрытие операций/значений.

Train: 32 разрешённых программы ×192 состояния, равномерно по длине, затем
по программе и состоянию. Validation: те же программы ×32 состояния.
Обычный test: те же программы ×оставшиеся 32 состояния.
Основные 6 новых программ оцениваются на всех 256 состояниях с разбивкой
192/32/32: это намеренный тест новых программ на знакомых и новых состояниях.
Контроль ADD,XOR,XOR оценивать отдельно, не добавлять к primary denominator.

Checkpoints выбирать каждые 250 updates по macro final joint accuracy,
усреднённой сначала по программам каждой длины, затем по длинам 1/2/3.
Tie-break: меньший validation loss при том же усреднении, затем ранний update.
Test не участвует в выборе и gate.

## Модели и супервизия

Текущий opcode подаётся явно, одинаково обеим моделям. Четыре применения
блоков QAT на инструкцию, один общий h между инструкциями; цикл блоков
фиксирован. Две выходные головы по 16 классов после каждой инструкции.
Не возвращать предсказанные или истинные регистры на следующий шаг.

Для программы длины L предлагаем один objective:
`(1/L) sum_j [CE(x_head(h_4j), x_j) + CE(y_head(h_4j), y_j)]`.
Это новый objective данной задачи, не утверждение эквивалентности E14 loss.
Для GRU использовать те же targets, точки супервизии и 4 внутренних
обновления на инструкцию. Примеры и порядок batches совпадают между arms.
Одинаковое число обновлений состояния и близкое число параметров не означают
равные FLOPs; CPU-время и параметры фиксировать отдельно.

До implementation clearance осталось определить:

1. Прямое представление начальных x,y, opcode и входной памяти. Не кодировать
   программу фиктивной pointer-table только ради совместимости старого parser.
   Любое изменение/отключение reader явно фиксировать как отличие от E14.
2. Размер GRU по формуле параметров до результатов; допуск относительно
   нового QAT arm ±5%, один выбранный размер, без поиска по accuracy.
3. Какая информация доступна в памяти: рекомендуемый минимальный первый
   тест даёт только текущий opcode и начальные регистры, без будущих команд.
   Иначе shared memory может позволить вычислить всю программу заранее.
4. Явное согласование gate, loss и внутренних шагов для обеих моделей,
   regression на отсутствие teacher forcing и независимая проверка encoder.

## Бюджет и критерии

Предлагаемый максимум: 2 arms ×3 seeds ×2000 updates ×batch64.
Итого 12000 updates, 768000 train examples. При одинаковом цикле длин
1/2/3 с концовкой 2/2 (666/668/666) — 6144000 внутренних обновлений
состояния по всем arms; QAT block applications и GRU updates учитывать
раздельно, не называть это равными FLOPs. Локальный CPU, без cloud/sweep.

Сначала обе модели seed0. Gate на validation-selected checkpoint каждой:
каждая одиночная операция ≥99% joint accuracy, каждая знакомая композиция
≥95%. На 32 состояниях это соответственно 32/32 и минимум31/32.
Если хотя бы одна модель не проходит gate, закончить paired pilot без
основного test inference и без подбора по нему. Отрицательная обучаемость
не равна провалу композиционного переноса. Если обе проходят — закончить
оба arms seeds1/2 до бюджета независимо от их результатов, без retries.

Primary для каждой модели отдельно: ≥244/256 joint final correct для
КАЖДОЙ из 6 новых программ в КАЖДОМ seed. Показать также полностью верные
трассы и все промежуточные joint counts. Не требовать выигрыша QAT над GRU,
если такой численный критерий не зарегистрирован до обучения.

Контроли до обучения: точный интерпретатор, таблицы одиночных переходов
с последовательным исполнением, перестановки порядка с одинаковым набором
команд, первое/последнее действие и identity. Символические контроли —
проверка семантики и коротких стратегий, не сопоставимые обучаемые модели.

Длины 4 и 6 — отдельные secondary-наборы без запрещённой пары и с ней.
Их список, эквивалентности и размеры требуется зафиксировать до обучения;
это ещё не готовые test manifests. Не смешивать их с основным тестом 2–3.
Замена поздней инструкции после общего префикса — отдельный заранее
заданный causal control, без изменения скрытого состояния на истинный ответ.

## Граница вывода и остановка подготовки

Даже полный успех показывает поведение на конечном DSL с явными opcode
и промежуточным loss. Он не доказывает специализацию блоков, необходимость
router, самостоятельное чтение программы, ветвление или языковой reasoning.
Следующий шаг — адресный design review и закрытие четырёх архитектурных
пунктов выше; после этого отдельная регистрация implementation/pilot.
