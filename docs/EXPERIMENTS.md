# Как сравнивать вычислительные бюджеты

Сначала выполните короткий sanity run из README. Команды ниже предназначены для отдельных исследовательских запусков; наличие команды не означает, что эксперимент уже проведён. Запускайте из корня проекта с активированным окружением.

## 1. Отдельно обученные модели

Первый эксперимент: обучить бюджеты **1, 4, 8, 16** на одинаковом потоке примеров для каждого seed и оценить каждый checkpoint только с его обученным бюджетом.

```bash
python scripts/sweep.py --mode separate-training \
  --config configs/multi_hop.json --out runs/cycle_budgets_equal_updates \
  --device cuda --updates 2000 --seeds 0 1 2 \
  --budgets 1 4 8 16 --budget-policy updates

python scripts/plot_results.py --mode separate-training \
  --inputs runs/cycle_budgets_equal_updates --out runs/cycle_budgets_equal_updates/plots
```

Одинаковые seed задают парное сравнение. Фиксированные evaluation-наборы должны совпадать между seed; скрипт графиков проверяет `suite_fingerprint`. При нескольких seed точки усредняются; полосы показывают одно выборочное стандартное отклонение между seed, а не доверительный интервал. Это сравнение разных обученных моделей. Оно не показывает, что одному checkpoint достаточно увеличить время инференса.

Равное число обновлений при одинаковом batch size означает равное число обучающих примеров, но большее число шагов увеличивает вычислительные затраты. В JSON сохраняются фактические `updates`, `examples_seen`, `example_steps` и `train_seconds`. Вариант с приблизительно равной суммой шагов ядра:

```bash
python scripts/sweep.py --mode separate-training \
  --config configs/multi_hop.json --out runs/cycle_budgets_core_steps \
  --device cuda --updates 2000 --seeds 0 1 2 \
  --budgets 1 4 8 16 --budget-policy core-steps --reference-steps 4
```

Здесь число обновлений равно `max(1, base_updates * reference_steps // steps)`: для указанного примера это 8000, 2000, 1000 и 500. Это **приближение стоимости**, исключающее фиксированные расходы, однократное создание памяти/K/V, особенности QAT, backward и работу ускорителя. При одинаковом batch size примерно совпадает число «пример × шаг ядра», но различается число свежих обучающих примеров. Ориентир для фактических затрат — измеренное время обучения; сравнивайте его на одной машине и устройстве. При ограничении числа обновлений снизу единицей или целочисленном округлении бюджеты могут заметно различаться.

## 2. Один checkpoint, разные бюджеты инференса

```bash
python scripts/sweep.py --mode checkpoint-sweep \
  --checkpoint runs/cycle_budgets_equal_updates/seed_0/steps_8/checkpoint_best.pt \
  --out runs/inference_budget --device cuda --budgets 1 4 8 16

python scripts/plot_results.py --mode checkpoint-sweep \
  --inputs runs/inference_budget --out runs/inference_budget/plots
```

Параметры здесь фиксированы. Нужно отдельно проверить, улучшает ли результат увеличение шагов. Глубина, отличная от обучающей, меняет распределение рабочих состояний; улучшение не гарантируется. Для модели, обученной с одним шагом, из A/B/C/D обучался только блок A: при четырёх и более шагах в вычисление впервые попадают необученные B/C/D. Поэтому checkpoint с обученными 8 шагами — более содержательная стартовая точка для этого эксперимента, хотя шаги 9–16 тоже не встречались при обучении.

## Чтение результатов

Проведённая CPU-абляция малого controlled-cycle конфига описана в [ONE_HOP_QUERY_ABLATION.md](../results/ONE_HOP_QUERY_ABLATION.md). В ней бюджеты 1 и 8 обучались отдельно при одинаковых updates/examples, а persistent-query сравнивался с восьмишаговым baseline. Одинаковый seed воспроизводит поток данных, но из-за дополнительного адаптера порядок инициализации общих весов между вариантами различается; это не парное сравнение одинаковых начальных весов.

Скрипт строит:

- `accuracy_vs_steps.png`: точность по вычислительным шагам;
- `accuracy_vs_hops.png`: точность по числу требуемых переходов;
- `accuracy_vs_time.png`: точность по измеренным мс/пример;
- `accuracy_vs_training_time.png`: точность по времени обучения, только для отдельных обучений.

На графиках времени числа возле точек означают вычислительные шаги. Мс/пример при пакетной оценке характеризует пропускную способность; это не задержка отдельного пользовательского запроса. Для времени сравнивайте одинаковые устройство, batch size, precision и условия прогрева/синхронизации. Не интерпретируйте небольшие различия как ускорение без повторных измерений. Пиковая CUDA-память доступна в evaluation JSON; на CPU/MPS поля CUDA равны `null`.

По умолчанию показаны `in_distribution` (новые таблицы, знакомые 1–4 перехода) и `longer` (новые таблицы, 5–8 переходов при том же алфавите `STEP`). Для validation добавьте `--splits validation in_distribution longer`. Пунктир случайного угадывания строится, если JSON содержит `num_objects`. В `evaluation.json` также записаны deterministic controls и agreement их предсказаний с моделью; совпавшие aggregate accuracy нельзя трактовать как совпадение алгоритма без этого agreement.

`configs/multi_hop*.json` используют один цикл через все 16 объектов и требуют `hops < 16`, поэтому внутри оценяемой траектории нет возврата в старт. `configs/base.json` оставлен в исходном functional-режиме для сопоставимости со старыми данными и checkpoint; там короткие циклы и неподвижные точки всё ещё возможны.

Эта задача проверяет повторное чтение памяти и изменение состояния. Даже успешный результат сам по себе не доказывает пользу нескольких разных операций, обучаемой маршрутизации, latent-черновика или адаптивной остановки. QAT симулирует низкую точность; упаковка весов и ускоренные тернарные CUDA-ядра здесь отсутствуют.

## Отдельная гипотеза: attention внутри каждого блока

Сейчас общий reader один раз строит K/V-память, а FFN-блоки получают уже прочитанное состояние. Следующая архитектурная идея — сделать каждый блок самостоятельной операцией чтения: у блока есть собственный обучаемый query `Q_i`, который читает общую K/V-память перед своим FFN-преобразованием. В простейшем варианте K/V остаются общими и кэшируются один раз, а меняется только query и, возможно, небольшой блоковый способ смешивания его с текущим `h`.

Гипотеза: разные блоки смогут специализироваться на разных стадиях операции и формировать более подходящее состояние для следующего чтения. Это прямо проверяет проблему текущей схемы, где reader может давать сильный сигнал только на первом шаге, а повторные FFN-визиты не обязаны выбирать следующий объект.

Проверять её нужно отдельной абляцией при фиксированных данных, числе параметров, числе вычислительных шагов и общей K/V-памяти. Сначала сравнить общий `Q` и block-specific `Q_i` на one-hop и fixed-two-hop. Если добавляются параметры, нужен контроль с таким же числом параметров, но без доступа блока к отдельному query. Результат будет свидетельством только для pointer-chasing задачи; он не докажет общую пользу block-specific attention для LLM. До этой проверки не добавлять одновременно router, halting, latent-записи или новые нормализации.

## Воспроизводимость и файлы

`sweep.json` сохраняет режим сравнения, конфиг, точные команды и число завершённых команд. `plot_metadata.json` связывает графики с checkpoint, seed и измеренными затратами. Графики отклоняют смешанные наборы данных, устройства, квантованный/float режим, число параметров, повторяющиеся seed/бюджеты и разный набор seed между бюджетами. При наличии полного конфига допускаются различия только в `model.steps`, `train.seed` и `train.updates`; значения batch size обучения и оценки должны быть одинаковы между сравниваемыми запусками. Проверяются также записанные аппаратные и программные характеристики среды. Обозначение `cpu` или `mps` само по себе не идентифицирует физическую машину; совпадение метаданных ещё не гарантирует одинаковые условия измерений. Используйте один исходный конфиг и одну машину для сравнения времени.

Каталог `--out` для sweep должен быть новым или пустым. Частично завершённый sweep автоматически не возобновляется: завершённые checkpoint сохранены, оставшиеся команды можно запустить отдельно из `sweep.json`. Восстановление отдельного обучения выполняется через основной CLI `train --resume`; его точная команда приведена в README. Скрипты запускают текущий Python через `sys.executable`, без shell, и поддерживают пути с пробелами.

Добавьте `--dry-run`, чтобы получить команды без обучения и создания файлов. Добавьте `--float` только к `separate-training`, чтобы провести отдельное диагностическое сравнение с обычными линейными слоями; не смешивайте эти результаты с QAT в одном вызове построения графиков. На CPU/MPS замените устройство и используйте маленький конфиг и число обновлений: целевая CUDA-машина не предполагается доступной в среде разработки.
