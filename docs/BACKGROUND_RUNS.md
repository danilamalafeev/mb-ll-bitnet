# Фоновые запуски с пробуждением

`run_and_wake.py` запускает одну команду в отдельной сессии и сразу возвращает
управляющему чату управление. После завершения процесса supervisor один раз
ставит в очередь сообщение в уже существующий Codex task. Между запуском и
завершением нет опроса Codex и нет автоматических повторов.

Пример из корня проекта:

```bash
python scripts/run_and_wake.py \
  --job-dir /tmp/e35-background-20260908 \
  --thread "$CODEX_THREAD_ID" \
  -- \
  python scripts/length_wave_e35_e36.py --help
```

`--job-dir` обязан указывать на ещё не существующий каталог: это защищает
артефакты от случайного смешивания двух запусков. Если `--thread` не указан,
используется `CODEX_THREAD_ID`; при отсутствии обоих параметров запуск
отклоняется. Путь к CLI можно заменить через `--codex`, например для
безопасного теста с fake executable. Используется локальная команда
`codex queue --thread UUID --message TEXT -C <cwd>`; флаг `--last` и создание
нового task не используются.

Команда после `--` передаётся как точный список аргументов с `shell=False`,
поэтому пробелы и shell-метасимволы не интерпретируются. Рабочий каталог —
текущий проект, из которого вызван launcher. В каталоге задания создаются:

- `status.json` — атомарно обновляемое состояние `start`, `running`,
  `completed` или `failed`, код выхода и состояние доставки;
- `stdout.log` и `stderr.log` — вывод дочерней команды;
- `queue.log` — результат единственной попытки доставки;
- `supervisor.log` — вывод detached supervisor.

При штатном завершении, ненулевом коде или ошибке запуска supervisor записывает
`delivery_status=pending`, затем делает ровно одну попытку `codex queue` и
сохраняет `queued` либо `failed` с кодом/ошибкой. Таймаут транспорта через 60
секунд записывается как `unknown`, поскольку сообщение могло быть принято.
Содержимое логов в сообщение
не копируется и не может стать инструкцией: wake-сообщение содержит только
абсолютные пути к статусу и логам и указание продолжить уже разрешённый
review/report по handoff. Для `failed` и `unknown` автоматического retry нет;
`status.json` и `queue.log` оставляются для ручной проверки.

## Доступ к очереди и проверка установки

CLI очереди должен иметь доступ на запись к локальному состоянию Codex. Внутри
ограниченного filesystem sandbox вычисление может завершиться, но доставка
получит ошибку read-only `state_5.sqlite`. Для фонового запуска из Codex используйте
обычное согласованное повышение разрешений только для конкретной команды launcher;
не добавляйте флаги обхода sandbox/approval и не расширяйте разрешения автоматически.
При отсутствии этого доступа нельзя обещать автоматическое пробуждение.

2026-09-08: шесть targeted tests прошли за 2.16 секунды, без вызовов модели.
Первый реальный smoke `runs/hook_smoke_20260908_01` сохранил успешный exit0 процесса
и ошибку доставки из-за read-only базы. Второй smoke с разрешённым доступом,
`runs/hook_smoke_20260908_02`, завершился exit0 и получил подтверждение native queue:
`delivery_status=queued`, одна попытка, queue exit0, message ID
`01a08167-c6d9-7b32-b26b-c77d5928faea`. Это подтверждает постановку в очередь;
возобновление ожидает завершения занятого хода целевой задачи. Автоматического retry
не было, выполнены только безвредные команды печати строки.

Для группы параллельных workers передайте launcher одну управляющую команду,
которая запускает группу и завершается после всех workers. Запишите в handoff
каталог задания и уже разрешённый следующий шаг, подтвердите запуск supervisor
и завершите активный ход. Reviewer не должен ждать без работы до появления файлов.

Полный smoke-цикл подтверждён: после завершения исходного хода сообщение из очереди возобновило ту же задачу. Проверены exit0, stdout `completion-hook-smoke-ok`, пустые stderr/supervisor logs и одна успешная доставка. Нового обучения или повторов не было.
